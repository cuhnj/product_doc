# 创优产品说明书（集中存储库）

本仓库用于集中存放创优（CUH）各产品线、各语言版本的产品说明书及相关派生资料，便于版本管理、检索与对外分发。远程默认指向公司内部 GitLab 上的 `cuh_product_doc` 工程（本地 remote 名一般为 `cuhgitlab`；具体 URL 以 `git remote -v` 为准）。

---

## 一、目录层级约定（四级结构）

仓库根目录下**仅允许**按下列四级组织内容（除本 `README.md`、`.gitignore` 等仓库元文件外，不随意在根目录堆放杂项）：

| 层级 | 含义 | 命名建议 | 示例 |
|------|------|----------|------|
| **一级** | 语言 / 区域 | 使用 BCP 47 风格小写+连字符，与内容语言一致 | `zh-CN`、`en-US` |
| **二级** | 产品家族 | 简短、稳定、全大写或 PascalCase，避免空格与特殊符号 | `SDVC` |
| **三级** | 产品规格 / 型号线 | 与对外型号或规格命名一致，便于按型号检索 | `SDVC34` |
| **四级** | 单本说明书「资料包」根目录 | 见下文「资料包文件夹命名」 | `cuh.sdvc34.manual.v0.0.zh-CN` |

逻辑路径示意：

```text
<语言>/<产品家族>/<产品规格>/<说明书资料包>/
```

当前仓库中的参考实例：

```text
zh-CN/
└── SDVC/
    └── SDVC34/
        └── cuh.sdvc34.manual.v0.0.zh-CN/
            ├── doc.md              # 主文档（含 YAML 头信息）
            ├── quality.json
            ├── report.json
            ├── ai/
            │   └── chunks/         # 分块/索引等（若由工具链生成）
            ├── data/               # 结构化数据、表格拆分等
            └── assets/             # 图片、整页渲染等（若存在）
```

说明：

- **三级目录**对应「某一规格/型号」的聚合；同一型号若有多语言，应在**不同一级语言目录**下各建一套四级资料包，而不是在同一语言下用子文件夹区分语言（避免与一级「语言」职责重叠）。
- **四级目录**是「一本说明书」的边界：版本迭代、质检报告、派生数据均建议收拢在该目录内，便于整包检出与归档。

## 二、资料包文件夹命名（四级）

为兼顾人工可读与自动化脚本解析，建议四级目录采用统一模式：

```text
cuh.<产品小写型号>.manual.<主版本>.<语言>
```

示例：`cuh.sdvc34.manual.v0.0.zh-CN`

- **`cuh`**：公司/品牌前缀，固定小写。
- **`<产品小写型号>`**：与物料或对外型号一致的小写标识（如 `sdvc34`）。
- **`manual`**：文档类型，说明书固定为 `manual`；若日后扩展类型（如快速入门），可改为约定词表中的其他值。
- **`<主版本>`**：说明书内容主版本，建议语义化或数字递增（如 `v0.0`、`v1.2`），与 `doc.md` 头信息中的 `version` 保持一致。
- **`<语言>`**：与一级目录语言一致，如 `zh-CN`。

若历史目录已使用简写（例如仅 `sdvc34`），新资料包**优先采用上述规范**；旧目录可在改版时逐步迁移，并在提交说明中注明迁移关系。

## 三、`doc.md` 与内容编写规范

### 3.1 文件头（YAML Front Matter）

主文档 `doc.md` 建议在文件首使用 YAML 头，便于工具链与检索系统消费，字段宜与仓库内已有示例对齐，例如：

- `doc_id`：全局唯一 ID，建议与四级目录名或 `doc_key`+语言 组合一致。
- `doc_key`：不含语言的逻辑键（如 `cuh.sdvc34.manual.v0.0`）。
- `doc_type`：如 `manual`。
- `lang`：与一级目录一致。
- `product`：产品标识（可与型号小写一致）。
- `title`：人类可读标题。
- `version`：与目录名/发布说明一致。
- `source_pdf`、`source_sha256`：若来源于 PDF 转换，记录来源与校验和，便于溯源与复现。
- `updated_at`：最近更新时间（建议 ISO 或统一约定格式）。

新增字段时，应在团队内同步约定含义，避免同一语义多个字段名。

### 3.2 正文（Markdown）

- 使用标准 Markdown 语法；表格、列表层级保持清晰，避免过深嵌套影响可读性与 diff。
- 章节标题层级连贯（如从 `##` 起为章，`###` 为节），与目录（TOC）结构一致。
- 插图、整页对照图等**相对路径**引用，路径以当前 `doc.md` 所在资料包为基准，避免写死本机绝对路径（历史文件中若存在绝对路径，新稿应避免）。
- 安全警示、法律责任、免责声明等固定模块保持醒目（标题与排版一致），多语言版本应对应同一结构，便于对照翻译。

### 3.3 质量与元数据

- `quality.json`、`report.json` 等若由转换或质检流水线生成，**随正文版本一并提交**，便于追溯该版本质量结论。
- `data/`、`ai/` 下文件若为自动生成，修改流水线后应重新生成并提交，避免手改与生成物长期不一致。

## 四、Git 与协作约定

- **分支**：默认以 `main`（或团队约定主分支）为发布基线；大改版可使用特性分支，合并前自检目录命名与 `doc.md` 头信息。
- **提交信息**：简明说明变更范围（如「新增 SDVC34 中文版 v0.1」「修正 zh-CN/SDVC/SDVC34 某章节笔误」）。
- **大文件**：若 PDF、高清图体积较大，需遵守公司 Git LFS 或大文件策略；本仓库 `.gitignore` 已排除常见日志、虚拟环境、密钥与临时目录，新增类型大文件前请先确认是否应纳入 Git 或改用制品库。
- **敏感信息**：禁止将密钥、内网绝对路径中的账号信息、未公开报价等写入仓库；`config.ini`、`.env` 等已在忽略列表中，亦勿强行提交。

## 五、与「说明书转换」工程的关系（可选）

若说明书由本地「说明书转换」等 Python 工程从 PDF 批量生成，建议：

- 生成输出目录映射到本仓库的**四级资料包路径**，保持 `doc_id`、`lang`、家族与规格目录一致。
- 转换脚本产生的临时文件、日志应放在该工程目录内，并依赖其自身的清理与日志滚动策略；**勿将临时目录提交到本仓库**。
